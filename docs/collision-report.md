# 碰撞面实测：「整词全拼音完全匹配」用于中文同音纠错

**测量对象**：`dsh-voice-personal` 里那套被删掉、现在想收紧后重新评估的中文同音纠正机制。

**要回答的问题**：如果把匹配条件收紧成（1）整词全拼音完全匹配、（2）音节数下限 L、（3）词条人工确认、（4）沿用现有无声调表，**碰撞面还剩多大**、**L 该取几**。

**测量脚本**：`test/collision.mjs`（纯 Node ESM，零依赖）。本文每个数字都能用 §10 的命令原样跑出来。

**算例编号**：本文所有语料相关数字都来自同一次运行（`generatedAt = 2026-10-16T10:50:43Z`，脚本 `--json` 头部会打印）。语料是活的（本次会话本身也写在 `~/.dsh/sessions` 下），隔几分钟重跑，窗口数会漂 ±0.1%。

**本文的纪律**：每个数字都标了**口径**（怎么算的）和**实测 / 推断**。凡是我没测出来、只是推算的，一律写明「推断」。

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 碰撞面随 L 怎么变 | **取决于口径，而且两个口径的答案方向相反**。全表枚举口径下**随 L 增长**（L=2 中位 5,561 → L=3 中位 618,540 → L=4 中位 5.55×10⁷）；语料实测口径下**随 L 急剧下降**（文本歧义率 64.09% → 14.03% → 1.31% → 0.30%） |
| 160,454 能否复现 | 能复现量级、复现不到末位。仓库里可考据的 7 个两音节键实测 **129,601**（= 160,454 的 **80.8%**）；剩下 5 个键的原始词条**没有落盘**，仓库、git 历史、会话记录、已安装 runtime 里都找不到 |
| L 该取几 | **L ≥ 4 是必要下限，但光靠阈值不安全**。必须再加一条**逐词条碰撞检查**（口径 B + D）。实测在 L=4 找到两个成员都是规范词的词对：`时间管理 / 事件管理`、`会议记录 / 会议纪录`（另找到 L=3 的 `服务器 / 服务期`） |
| 有没有反例 | **有，L=3 和 L=4 都有**，而且用真引擎跑出来确实改错了正文（见 §6）。**L=5 没找到词对反例**，但语料里仍有 97 个键发生碰撞 |
| 最大不确定性 | 语料只有 **48.7 万汉字**、单人、5 天、技术话题，且**不是听写输出**。碰撞数随语料体积增长且**没饱和**（L=4 歧义率从 2.8 万字的 0.11% 涨到 48.7 万字的 1.31%；拟合增长指数 0.48–0.87，见 §9.1），所以实测最大值（L=4 为 3）是**下界**；外推到 1000 万汉字，L=4 的歧义率约 **4%–18%**（推断）。另外跨语料对半切显示：L≥4 的碰撞键**身份完全不重叠**（两半共同碰撞键 = 0），意味着任何固定语料都枚举不完危险集 |

## 1. 四种口径（必须先分清，否则结论会互相打架）

同一个问题「这个键会命中多少个串」，有四种算法，答案差好几个数量级：

| 口径 | 定义 | 性质 |
|---|---|---|
| **A 全表枚举** | 键 = 音节串，碰撞数 = ∏\|chars(音节)\|，即 26,711 字的表里有多少个 L 字串的键等于它 | 上界。**这就是 160,454 的口径**。随 L 增长（因子变多） |
| **B 语料实测** | 真实语料里实际出现过的、共用该键的**不同 L 字串**个数 | 直接证据。随 L 急剧下降 |
| **C 常用字枚举** | 把字表限制到语料字频前 K 个字再算 ∏ | 模型（推断），估计「像人写的」串有多少 |
| **D 词表对撞** | 给一份真实词表，找同键词对 | 与语料无关，专抓「两个都是正经词」的最小对立对 |

> **A 涨、B 降，两者之差的来源是「生僻字不可能被写出来」，不是音节数本身。**
> 这一点决定了后面的结论：**用哪个口径当判据，就会得出相反的 L 建议**，所以判据必须先定义清楚。

口径 A 的算法在脚本里是闭式乘积（`languageCollisions`），**不枚举**——因为 L=3 的碰撞空间是 26711³ ≈ 1.9×10¹³ 个串，物理上枚举不完。这也说明「全表碰撞数」在 L≥3 时已经不是「会误伤多少串」，而是一个纯组合计数。

**两个工程细节，都会影响数字，必须说清：**

1. **会话是「多帧」zstd，Node 的 `zlib.zstdDecompressSync` 只解第一帧**。直接用它只会拿到 288 字节的会话头，而语料实际是 1.5 MB 文本。脚本自带帧遍历（走块头定界、不解压），解压结果与 `zstdcat` 一致。

**语料性质的坦白**：这是**写出来的中文**，而且 88.7% 是模型产出的技术散文（user 段只占 11.3%）。它**不是语音转写输出**，所以观察不到真正的错误面（ASR 把「工作台」听成「工作太」这类）。本机没有转写日志：`~/.dsh/speech-to-text` 只有模型权重，`~/.dsh/voice-personal/style.json` 只有派生统计（`stats.cjkChars = 8,716`，来自 158 条听写文本），没有原文。

## 4. Q1：碰撞面随音节数的变化（**实测**）

语料：486,865 汉字。窗口 = 所有汉字连续段上的滑动窗口；跨度里有字不在表里就跳过（「整词全拼音」要求每个字都有读音）。实测跳过数为 **0**——这 1,874 个常用字全在表里。

### 4.1 主表：一个 L 字拼音键，平均/中位/最大有多少个**不同的 L 字串**共用它

| L | 窗口数 | 不同串 | 不同键 | **每键实测串数** 平均 / 中位 / p90 / p99 / **最大** | 碰撞键占比 | **文本歧义率** |
|---|---|---|---|---|---|---|
| 2 | 387,655 | 46,815 | 27,808 | 1.68 / **1** / 3 / 8 / **33** | **34.57%** | **64.09%** |

## 7. Q4：跨语料稳定性（**实测**）

按会话 `createdAt` 中位数把 94 个会话切成两半：

| | 会话 | 汉字 | L=2 歧义率 | L=3 | L=4 | L=5 |
|---|---|---|---|---|---|---|
| 旧半 | 47 | 427,049 | 61.78% | 12.93% | 1.27% | 0.294% |
| 新半 | 47 | 59,816 | 30.51% | 2.90% | 0.18% | 0.062% |

单键最大碰撞数：L=2 `28 / 12`，L=3 `8 / 4`，L=4 `3 / 2`，L=5 `3 / 2`。

两半**共有键**的碰撞数是否一致：

| L | 共有键 | 计数一致 | 旧半碰撞键 | 新半碰撞键 | **两半都碰撞** | 只在一半出现 |
|---|---|---|---|---|---|---|
| 2 | 6,845 | 46.7% | 8,532 | 1,425 | 1,164 | 7,629 |
| 3 | 4,994 | 82.9% | 4,055 | 281 | 104 | 4,128 |
| 4 | 1,487 | **97.5%** | 447 | 19 | **0** | 466 |
| 5 | 395 | **99.2%** | 79 | 6 | **0** | 85 |

**两条结论（都是实测得出，不是猜测）：**

1. **L=2 的碰撞面严重依赖话题**：只有 46.7% 的共有键计数一致，7,629 个键只在一半出现。新半语料只有旧半的 1/7，歧义率就从 61.8% 掉到 30.5%——**说明这个数字本身就是语料规模的函数**。
2. **L≥4 时，碰撞键的身份完全不重叠（两半共同碰撞键 = 0）**。共有键的计数一致率虽然高达 97.5%，但两边各自新出现的碰撞键**彼此毫无交集**。这意味着：危险键的产生是**随机的、话题特有的、不复现的**——**任何固定语料都无法把危险集枚举完**，只能给出发生率。

> 这条直接决定了下一条建议：**逐词条检查必须在「加入词条的那一刻、对着用户自己的语料」跑，不能靠一份预先算好的黑名单。**

## 8. Q5：结论——L 取几，判据是什么

### 8.1 判据定义

我把「安全」定义成三条**合取**，按优先级排列：

| # | 判据 | 为什么合理 |
|---|---|---|
| **S1** | 给定词条（键 K → 规范形 Y），**语料 + 词表里不存在任何 ≠Y 的、真实出现的串 S 使得 key(S)=K** | 这是假阳性的充要条件。碰撞数不为 0 就意味着有一整类句子会被改错；碰撞数为 0 则该词条在这份语料上**按定义不可能误伤**。比「阈值」强得多，因为它可判定、可复现、可写进测试 |
| **S2** | L ≥ 4 | 实测文本歧义率：L=2 64.09%、L=3 14.03%、L=4 1.31%、L=5 0.30%。L=3 仍有 5.67% 的键天生歧义，且存在 `服务器/服务期` 这种两个规范词的对撞；L=4 降到 0.59%，把「漏网的」压到词表检查能兜住的量级 |
| **S3** | 词条人工确认 | 现状已经如此，不多说 |

**为什么不把 S2 单独当判据**：L=4 实测存在 `时间管理/事件管理`、`会议记录/会议纪录` 两个规范词对撞，**所以「L=4 就安全」是错的**。反过来，**「阈值越高越安全」也不成立**：L=5 语料里仍有 97 个碰撞键（`我必须先就/我必须先纠` 各 4 次）。**任何有限 L 都存在反例，L 只能把发生率压低，不能归零。**
**为什么不取 L=5**：L=5 并不会比「L=4 + S1 检查」更安全（S1 保证 0 误伤，L=5 只把发生率从 1.31% 压到 0.30%），却会砍掉大量真实术语——中文领域词绝大多数是 2–4 字（服务器 3、数据库 3、浏览器 3、工作台 3、人工智能 4、机器学习 4），而且这位用户 `style.json` 里最高频的 60 个听写短语**全部是 2–3 字**（实测：长度集合 {2,3}，最长 3 字，同键组 0 个）。用 L=5 换 1 个百分点的发生率下降，代价是功能基本不可用。

### 8.2 建议（明确）

> **L_min = 4，并且必须叠加逐词条碰撞检查（S1）。**
> **不要只用阈值。** 如果因为工程原因做不到逐词条检查，那么**任何 L 都不该上线**——包括 L=5。

实现 S1 的成本很低，脚本已经给出三档检查：

```bash
node test/collision.mjs --keys <新词条的键>                          # 口径 A：先看组合规模
node test/collision.mjs --corpus <用户语料> --lengths 4 --examples   # 口径 B：语料里有没有同键串
node test/collision.mjs --wordlist <常用词表> --corpus <用户语料>     # 口径 D：有没有同键词对
```

任一步发现 **≠ 目标词的**同键串，就拒绝该词条，或降级为「只做提示、不改写」。

### 8.3 如果一定要给一个「不加检查」的量化预期

**推断**（由实测的规模增长曲线外推，不是实测）：

| L | 文本歧义率（48.7 万汉字，实测） | 外推到 ~1000 万汉字（推断，指数取 0.4 / 0.5 / 0.87 三档） |
|---|---|---|
| 2 | 64.09% | 已饱和，≈ 64%（外推无意义） |
| 3 | 14.03% | 47% / 64% / 饱和 |
| 4 | **1.31%** | **4.4% / 5.9% / 18.1%** |
| 5 | 0.30% | 1.0% / 1.4% / 4.2% |

外推依据见 §9.1。**这个区间很宽，正是「语料不够」的直接代价**：按乐观端（指数 0.4）L=4 在 1000 万汉字下约 4%，按悲观端（指数 0.87）接近 18%。两者都远高于本报告的实测值 1.31%——所以 §8.1 的 S1（逐词条检查）不是可选项，而是这个外推区间下唯一能给出确定性的手段。

## 9. Q7：不确定性（哪些结论是语料不足、无法判定的）

### 9.1 语料规模不够，且这是系统性的（**实测**曲线 + **推断**外推）

把语料按固定随机种子打乱后取前 x% 重测（实测）：

| 语料占比 | 汉字 | L=2 最大/歧义率 | L=3 最大/歧义率 | L=4 最大/歧义率 | L=5 最大/歧义率 |
|---|---|---|---|---|---|
| 5% | 28,355 | 11 / 29.55% | 3 / 2.50% | 2 / 0.11% | 2 / 0.02% |
| 10% | 55,408 | 16 / 37.88% | 4 / 4.61% | 2 / 0.37% | 2 / 0.12% |
| 25% | 128,352 | 20 / 49.43% | 7 / 7.89% | 2 / 0.69% | 2 / 0.16% |
| 50% | 255,544 | 24 / 56.66% | 8 / 10.98% | 3 / 0.92% | 2 / 0.23% |
| 75% | 368,040 | 28 / 61.28% | 8 / 12.73% | 3 / 1.15% | 3 / 0.26% |
| **100%** | **487,470** | **33 / 64.14%** | **8 / 14.05%** | **3 / 1.31%** | **3 / 0.30%** |

（末行是同一语料的另一次打乱运行，汉字数与 §3 的 486,865 差 0.1%，属正常漂移——语料是活的。）

- **没有任何一个 L 的值饱和了**（只有 L=3 的「单键最大」在 50% 之后停在 8，以及 L=2 的歧义率本身已接近上限）。把「歧义率 ∝ 体积^k」拟合一遍（推断）：

  | L | k（5%→100%） | k（50%→100%） | k（25%→100%） |
  |---|---|---|---|
  | 2 | 0.272 | 0.192 | 0.195 |
  | 3 | 0.607 | 0.382 | 0.432 |
  | 4 | 0.871 | 0.547 | 0.480 |
  | 5 | 0.952 | 0.411 | 0.471 |

  低体积端接近线性（k≈0.9），高体积端减速到 k≈0.4–0.55——**符合「同键串两两相遇」的饱和型增长**，而不是幂律。外推时我取 0.4–0.87 作为区间（§8.3）。所以：
  - 表格里的「最大碰撞数」（L=4 为 3、L=5 为 3）**是下界**，语料更大时还会涨。
  - 「L=4 占比 0.59%」也是下界。
- **无法判定的部分**：真实用户一辈子的听写量远大于 48.7 万汉字。按 0.4–0.87 的指数外推到 1000 万汉字，L=4 歧义率落在 **4.4%–18.1%**、L=5 落在 **1.0%–4.2%**。**「L 取几才能把发生率压到可忽略」这个问题，这份语料答不了**——区间宽到足以改变结论（乐观端 4% 或许可接受，悲观端 18% 显然不可接受）。

### 9.2 语料性质不对口（结构性缺陷）

- 88.7% 是模型写的技术散文，不是听写产物。**真机错误面（ASR 把 A 听成 B）在这份语料里根本不存在**，所以本文所有「碰撞」都只覆盖了「原本正确的文本被误改」这一半；另一半（该改的没改、召回率如何）完全没测。
- 只有 55,061 汉字来自人写的消息，其中很多还是子代理任务书（AI 代笔）。**真正由本人敲/说出来的中文可能只有 1–2 万汉字**，统计上很薄。
- 单一用户、单一领域（DSH / 语音插件 / 游戏）、5 天。§7 的稳定性结论说明话题换了碰撞键就换。

### 9.3 无法复现的部分（诚实标注）

- **160,454 复现到 129,601（80.8%），差的 5 个键确实找不到了**。本文论证它「合理」（落在 p75–p90 区间），但**这不是复现，是佐证**。
- 原始 12 组词条的字面清单不存在于本机任何位置（已查：仓库、git 历史、全部会话正文、已安装 runtime、`paperclip-data`）。

### 9.4 口径本身的局限

- 口径 A 在 L≥3 时是纯组合计数，**不是风险度量**。任何拿它当「碰撞面」的结论（包括 160,454 那个数字本身用来论证 L=3 的必要性）都要打折。
- 口径 C（常用字枚举）假设「字独立组合」，会**高估**：L=4 前 1000 常用字下中位 288，而实测中位 1。它只能当上界看。
- 口径 B 依赖语料里恰好同时出现同键的两个串，**必然低估**（§6.3 已用三个真词对验证：在这份语料里出现 0 次）。
- 本文所有「引擎实测」都用了 `pairs` 注入词条，走的是 `fixCrossScript` 那条真实代码路径（L≥3、整段读音齐全、键完全匹配）。但它**没有系统测试多词条重叠时的贪婪最长匹配行为**——`把时间管理和事件管理分开` 那一行的连锁改写只演示了一次。

```js
// §9.1 的增长曲线：打乱语料后取前 x% 重测（这就是本文那张表的来源）
import { PinyinIndex, walkCorpus, readSession, measureLength } from './test/collision.mjs';
const py = new PinyinIndex();
const docs = [];
for (const f of walkCorpus(`${process.env.HOME}/.dsh/sessions`)) {
  const s = readSession(f);
  if (!s?.docs.length) continue;
  if (s.docs.some((d) => /整词全拼音匹配|碰撞面随音节数的变化/.test(d.text))) continue; // 元污染
  docs.push(...s.docs);
}
for (const frac of [0.05, 0.1, 0.25, 0.5, 0.75, 1]) {
  const sub = docs.slice(0, Math.floor(docs.length * frac));   // 正式跑应先按固定种子打乱
  for (const L of [2, 3, 4, 5]) {
    const m = measureLength(sub, L, py);
    let max = 0, ambTok = 0, tok = 0;
    for (const [, g] of m.byKey) {
      if (g.size > max) max = g.size;
      for (const v of g.values()) { tok += v; if (g.size >= 2) ambTok += v; }
    }
    console.log(frac, `L=${L}`, 'max', max, '歧义率', (100 * ambTok / tok).toFixed(2) + '%');
  }
}
```
